# M1 engine core: decisions made while building it

Collected from the execution ledger when M1 finished (2026-10-27), before the ledger was deleted.
Each ruling reads: what was decided — why — what it costs if wrong.

## Rulings (43)

- Ruling (pre-flight): T5 maps every CapReached to stop_kind "cap_daily" — extraction is essential, so only the daily cap can block it (Step 5's allowed()) — cost if wrong: a monthly-cap stop would wait until midnight instead of retrying sooner, but it cannot occur for purpose "extract".
- Task 2: Ruling: kept test_the_prompt_explains_needs_action — it asserts the output of system_prompt(), the text the model actually receives, as the existing prompt tests do; it is not a grep of source — cost if wrong: one wording-coupled assertion to update if the prompt line is reworded.
- Task 3: Ruling: the brief's "existing sync tests must pass unchanged" contradicts its own Produces block (messages not kept count as skipped; test expects (1, 4)) — followed the Produces block: sync now counts your own sent mail and unparseable mail as skipped, so two test_cli expectations moved (2,0)→(2,1) and (1,0)→(1,1), the parse-error test patches ingest.build_mail_item, and `assistant sync` prints "N skipped (already stored or not kept)" instead of "already stored" — cost if wrong: a cosmetic change to one count in the sync summary.
- Task 3: Ruling: build_query moved to ingest (cli re-exports it) and ingest imports the Google libraries inside its functions — avoids a cli↔ingest import cycle and keeps `list`/`stats` free of Google imports as before — cost if wrong: none functional.
- Task 4: Ruling: check_mail uses the feed only when both gmail_history_id and gmail_address are stored; a bookmark without an address takes the fallback (profile first, then search) — the feed path needs the address for to_me, and a second getProfile just for it would blur which call set the bookmark — cost if wrong: one extra search after a half-written state, which only an interrupted first check can leave.
- Task 5: Ruling: each worker task opens and closes its own Store, not one per thread — a sqlite3 connection can only be closed in the thread that opened it, so per-thread stores could not be closed in the run's finally; opening one costs ~1 ms against seconds per model call — cost if wrong: a few ms per email.
- Task 5: Ruling: RunReport.stop keeps the first stop reason, except that "fatal" replaces a passing one (busy, no_answer, call_limit, cap_daily) — with several workers a 429 and a 401 can land together, and the 401 is the one the owner must fix (Task 8 maps fatal to a 60-min backoff and an "anthropic" problem) — cost if wrong: a busy stop reported as fatal never happens; a fatal one is never hidden.
- Task 5: Ruling: a crash in our own code inside a worker sets the stop event, lets the pool drain, and is re-raised from run_extraction — the same propagation as the inline path, where the claim's counted attempt gives the email up after 3 runs — cost if wrong: none beyond the inline behaviour.
- Task 6: Ruling: the wake check measures from the END of the previous tick, and a job's next due time from when it finished — otherwise an extraction run longer than 3 minutes would look like a sleep and re-run every job, and a 1-minute job that ran 3 minutes would be due again at once — cost if wrong: a backwards clock change during a job is caught one tick later.
- Task 6: Ruling: run_soon for a job later in the registration order runs it in the same tick (check_mail → extract), as tick checks each job when it reaches it — the spec wants extraction "right after" new mail; waiting a 15 s poll would add latency for nothing — cost if wrong: none; a job asking for itself still waits a tick.
- Task 7: Ruling: EngineLock.acquire(wait_seconds=2.0) retries for up to 2 s before raising EngineRunning — measured on this PC, Windows frees a killed holder's lock 15–30 ms after the process ends (documented: "depends upon available system resources"), so a restart right after a crash was refused; the death test now acquires straight after the kill — cost if wrong: a second engine start waits 2 s before being told one is running.
- Task 7: Ruling: on Windows the lock is one byte at offset 1 MiB, not byte 0 — Windows locks are mandatory, and locking byte 0 would make the PID written "for humans" unreadable to every other process — cost if wrong: none (locking past end-of-file is allowed and writes nothing).
- Task 8: Ruling: test_new_mail_makes_extraction_run_at_once asserts that the next tick runs extract, not next_due("extract") == now — Task 6's scheduler records run_soon as a flag and leaves the due time alone; the behaviour the brief wants (extract without waiting its interval) is what the test pins — cost if wrong: none.
- Task 8: Ruling: an offline check also sets last_check_error ("offline"), not only a lost login — it is the same state key, check_mail clears it on success, and the dashboard (M2/M3) can show either from one place — cost if wrong: one extra state write per failed check.
- Task 8: Ruling: ExtractJob takes an extra keyword clock=utc_now (passed to run_extraction for the cost ledger), and the "anthropic" problem's detail passes through vault.redact — keeps the ledger on real time and any key-shaped text out of events — cost if wrong: none.
- Task 8: Ruling: ProfileWatchJob marks a modification time as seen only after load_profile returns or raises ConfigError; any other failure (a file locked mid-save) propagates to the scheduler and is retried 30 s later — cost if wrong: a repeated job_error log line while a file stays unreadable.
- Task 9: Ruling: run_engine runs the scheduler on a daemon "engine" thread and the main thread waits in 0.2 s sleeps; the first Ctrl+C sets stop and lets the running job finish, a second quits at once — measured here: Event.wait(8) ignored a SIGINT for the full 8 s on Windows/Python 3.12 while time.sleep was interrupted in 1.0 s, so the brief's "Ctrl+C becomes a clean stop" needs this; letting the job finish keeps a paid reply from being thrown away — cost if wrong: a second Ctrl+C mid-extraction counts one attempt on the email in flight.
- Task 9: Ruling: the Engine (and its Store) is built on the engine thread, which signals ready before the banner prints; a start failure (broken profile.toml, locked database) is re-raised in the main thread and the lock is released — a sqlite3 connection can only be used by the thread that opened it — cost if wrong: none.
- Task 9: Ruling: on_error's log line ends with the failing frame's location "(at file.py:line in function)" — data-free (no locals, no message beyond the redacted one) and makes an always-on engine's crash findable — cost if wrong: one extra clause per error line.
- Task 10: Ruling: declined [10] "a max_tokens retry that lands on the 60-call limit throws its paid first reply away" — letting retries pass the limit breaks the hard "at most 60 model calls a run" constraint; the waste needs a rare max_tokens reply to coincide with the limit, at most one per worker (≤ 4 × ~$0.002) — cost if wrong: a few cents a month at worst.
- Task 10: Ruling: Task 6's ruling understated a backwards clock change during a job ("caught one tick later"): it was never caught, and is fixed as finding [6].
- Task 10: Ruling: [13] an email whose call never answers counts an attempt only when another call in the same run was answered; when nothing answers, the run's no-answer emails are unclaimed — distinguishes "this email" from "Anthropic is down" without a schema change — cost if wrong: an outage that starts mid-run, three runs in a row, could give up one email early (its body then expires as it would at 7 days anyway).
- Task 10: Ruling: run_extraction's stop_kind gains "offline" (no connection: nothing sent) and "cancelled" (the engine is stopping) — ExtractJob maps offline like busy and cancelled to no backoff — cost if wrong: none; the plan's five kinds keep their meaning.
- Task 10: Ruling: test_a_busy_api_stops_the_run_without_counting_against_the_email lost its LlmNoAnswer case — a no-answer no longer stops a run at once ([13]); its new behaviour has three tests of its own — cost if wrong: none.
- Task 10: Ruling: STATUS events now carry "source" (gmail, anthropic, profile, job:<name>) and the EventBus keeps current problems per source (report/problems) — the plan's flat {"problem": ...} let a good mail check clear a still-true key or profile problem ([15]) — cost if wrong: M2's API and M3's dashboard read the new shape (no consumer exists yet).
- Task 10: Ruling: Engine takes stop= and run() takes only poll_seconds — ExtractJob needs the engine's stop at construction to cancel extraction ([5]), and one event for both avoids two that drift — cost if wrong: none; run_engine is the only caller.
- Task 10: Ruling: the first failed mail check retries in 30 s without reporting "offline"; the spec's 5 -> 15 min schedule follows from the second failure — after a wake Wi-Fi is often still connecting, and the spec's own 2-minute promise was broken by a 5-minute first step ([18]) — cost if wrong: one extra failed check per outage.
- Task 10: Ruling: [3] is half-fixed by design: the feed applies the query's label exclusions (-in:, -category:) and the engine warns at start about any other term (from:, -label:<own>, OR) — matching arbitrary search terms would need a search per new email, and Gmail's search index can lag a just-arrived message, which would then be missed for good — cost if wrong: an owner with a from:-style query sees those emails extracted (pre-filter and profile drop rules still apply), with a warning saying so.
- Task 10: Ruling: [12] treats only a zero-byte profile.toml as mid-save — a half-written non-empty file is either invalid TOML (reported, old profile kept) or valid and corrected by the editor's next write within 30 s — cost if wrong: at most one 30-second window ranked against a partial profile.
- Task 10: Ruling: [19] gives back attempts only for 'pending' extract ledger rows; a kill in the instant between claim and reserving the call is not covered — that window has no network wait in it — cost if wrong: one counted attempt in a rare case.
- Task 10: Ruling: [11] EngineRunning names the holder: the engine keeps the plan's message, a CLI writer gets "`assistant <command>` is still running in another window" — once CLI writers hold the lock, an engine started during `assistant sync` would otherwise be told an engine is running — cost if wrong: none.
- Task 11: Ruling: the README step (4) is committed ahead of the smoke re-recording (steps 1-3), which waits for the owner's approval of a paid call — documentation needs no approval and should not sit uncommitted — cost if wrong: none; Task 11 then lands in two commits.
- Task 12: Ruling (owner, 2026-10-27): D6 not done — Google Auth Platform greys out "Publish app" with "complete your configuration on the Branding page" although app name, support email and developer contact are saved (a known, unanswered report on discuss.google.dev, Oct 2026). The live check runs on a Testing-mode 7-day sign-in; the engine already reports auth_lost and picks up a new `assistant auth` without a restart — cost if wrong: one `assistant auth` a week until publishing works.
- Final: Ruling: re-graded Minor #1 (a new `assistant auth` / `set-key` noticed only after 15 / 60 min) to Important — with D6 blocked the owner re-signs in weekly, so the delay recurs every week, and the docs promised "as soon as" — cost if wrong: one extra fix in this pass.
- Final: Ruling: the Task 10 ruling "ExtractJob maps offline like busy … cost if wrong: none" was wrong: a 20-min Wi-Fi loss with mail queued delayed new mail by up to an hour (reviewer probe p1); fixed below.
- Final: Ruling: v6 sightings backfill keeps only first_message_id — the plan's frozen SQL, and pre-v6 merged sightings were never recorded, so nothing is recoverable — cost if wrong: older opportunities show fewer source emails.
- Final: Ruling: a stored gmail_address is not compared with the signed-in account after an account switch — the owner has one inbox by design (mail routing note) — cost if wrong: a switched account would read from the old bookmark until it expires (one fallback search).
- Final: Ruling: mail moved out of an excluded category (Promotions -> Primary) is not rescued by the feed — part of ruling [3]'s accepted half-fix; the default query excludes no category — cost if wrong: only owners who exclude categories miss a re-categorised email.
- Final: Ruling: one message whose fetch fails persistently with a non-404 error would block the feed — no evidence Gmail does this; the error goes to the scheduler as job_error every 2 min, so it would be visible — cost if wrong: mail checks stall until the message changes.
- Final: Ruling: log rotation while another process holds engine.log open without delete sharing — rare at this volume (1 MB of id-only lines lasts weeks) and environment-specific — cost if wrong: one rotation error in the log.
- Final: Ruling: a model call hung after wake (up to the 120 s timeout) blocks check_mail for that time — the plan's one-scheduler-thread design; 120 s is inside the 2.5-min target's slack — cost if wrong: one mail check up to 2 min late after a wake.
- Final: Ruling: `extract --estimate` (its sweep) and `llm smoke` (a ledger row) still write while the engine runs — the plan allows them; both are short, single transactions under SQLite's busy timeout — cost if wrong: none observed (the live check ran smoke before the engine).
- Final: Ruling: EngineRunning's message says "Use the dashboard" though M1 has no dashboard — the plan's fixed text, true from M3 — cost if wrong: a confusing word until M3.
